# PyPI Supply Chain Monitor — спецификация

Oct 30, 2026 · @Vladimir

## Цель и рамки

Сервис непрерывно следит за новыми релизами на PyPI и поднимает алерт, когда релиз похож на supply chain атаку. Главная ниша, которую не закрывает GuardDog: **анализ изменений между версиями** уже существующих пакетов (захват аккаунта мейнтейнера, внедрение кода в обновление).

**Входит в проект**

- Поток всех новых пакетов и релизов PyPI почти в реальном времени.
- Четыре слоя детектирования: метаданные, статика (GuardDog как движок), дифф между версиями, анализ репозитория и релизного процесса.
- Динамический анализ в песочнице — отдельный, поздний этап.
- Риск-скоринг, алерты в Telegram, простой веб-дашборд.
- Оценка качества на открытом датасете вредоносных пакетов.

**Не входит (non-goals)**

- Другие экосистемы (npm, crates) — архитектура должна позволять добавить их позже, но не в этой версии.
- Блокировка установки у пользователей (pip-плагин, прокси-зеркало).
- Автоматическая отправка репортов в PyPI без ручной проверки.

**Критерии успеха**

- Задержка от публикации релиза до вердикта — не больше 10 минут для 95% релизов.
- Recall на датасете вредоносных пакетов — не ниже, чем у GuardDog в стоковой конфигурации.
- Не больше 20 алертов в день на ручную проверку, иначе сервисом невозможно пользоваться.
- Хотя бы один найденный и подтверждённый PyPI вредоносный пакет.

## Источники данных

Основной поток релизов берём из RSS-фидов PyPI, детали и артефакты — из JSON API. Популярность пакетов нужна для поиска тайпсквоттинга и приоритизации диффов.

| Источник | Что даёт | Как используем |
| --- | --- | --- |
| RSS `pypi.org/rss/updates.xml` | Последние обновления (новые версии) | Опрос каждые 30–60 с, дедупликация по (пакет, версия) |
| RSS `pypi.org/rss/packages.xml` | Новые пакеты | Тот же поллер |
| XML-RPC `changelog_since_serial` | Все события по serial-номеру | Резервный канал, догон пропусков после простоя |
| JSON API `pypi.org/pypi/<name>/<ver>/json` | Метаданные, список файлов, хэши, URL | Обогащение релиза, скачивание sdist/wheel |
| Simple API (PEP 691) | Список всех версий пакета | Выбор предыдущей версии для диффа |
| Список топ-пакетов по загрузкам (BigQuery `pypi` или готовые выгрузки) | Популярность | Эталон для тайпсквоттинга, приоритет диффов |
| DataDog `malicious-software-packages-dataset` | Тысячи реальных вредоносных пакетов | Оценка recall, обучение скоринга |
| OpenSSF `malicious-packages` (формат OSV) | Отчёты о малвари с ID | Разметка, сверка с нашими находками |

Открытый вопрос: точные лимиты и глубина RSS-фидов — проверить на практике в первой задаче, от этого зависит частота опроса.

## Модули детектирования

Каждый модуль — независимый анализатор с единым интерфейсом: на вход релиз, на выход список сигналов `{rule_id, severity, confidence, evidence}`. Новые анализаторы добавляются без изменения пайплайна.

### 1. Метаданные

- Тайпсквоттинг: Левенштейн и Дамерау до топ-5000 пакетов, замены `-`/`_`/`.`, перестановки, префиксы и суффиксы (`python-`, `-py`, `2`).
- Подозрительный профиль: пакет моложе 24 часов, первый релиз аккаунта, пустой или скопированный README, нет ссылки на репозиторий.
- Несоответствие: `project_urls` указывает на чужой популярный репозиторий.
- Только sdist без wheel при наличии `setup.py` с логикой.

### 2. Статика (GuardDog)

- Запуск GuardDog как библиотеки на распакованном артефакте, нормализация его вывода в общий формат сигналов.
- Свои правила Semgrep/YARA поверх: Discord/Telegram-вебхуки, доступ к браузерным профилям и криптокошелькам, загрузка и запуск бинарников, `exec` от декодированной строки.
- Энтропия строк и доля обфусцированного кода как отдельный сигнал.

* **Крипто-стилеры** (отдельный набор правил): чтение каталогов кошельков (Exodus, Electrum, Atomic, расширения MetaMask и Phantom в профилях браузеров), подмена буфера обмена (`pyperclip`, `win32clipboard` вместе с регулярками адресов BTC/ETH/SOL), встроенный словарь BIP39 и поиск seed-фраз, жёстко прописанные адреса кошельков в коде.

### 3. Дифф версий (ключевая фича)

Для нового релиза существующего пакета сравниваем его с предыдущей версией и анализируем **только изменения**.

- Файловый дифф: новые файлы, изменённые `setup.py`, `__init__.py`, `.pth`-файлы, entry points.
- AST-дифф: новые импорты (`socket`, `requests`, `base64`, `ctypes`), новые вызовы `exec`/`eval`/`subprocess`, новые строковые литералы с URL и IP.
- Сигналы контекста: смена мейнтейнеров, релиз после долгого затишья, version jump, расхождение между sdist и wheel, расхождение с тегом в GitHub-репозитории.
- Приоритет: пакеты из топа по загрузкам анализируются первыми и с более низким порогом алерта.

### 4. Динамика в песочнице (поздний этап)

- `pip install` и `import` в изолированном контейнере (gVisor или Firecracker), без доступа к реальной сети.
- Запись сетевых попыток (DNS, TCP), файлового доступа к чувствительным путям (`~/.ssh`, `~/.aws`, профили браузеров), порождённых процессов.
- Honeytokens в окружении: фейковые AWS-ключи, токены, файлы криптокошельков и seed-фраза, плюс адрес кошелька в буфере обмена для ловли подмены — любое обращение к ним сразу считается критичным.
- Запускается только для релизов с риском выше порога после статики, чтобы экономить ресурсы.

### 5. Репозиторий и релизный процесс

Сопоставляем релиз на PyPI с тем, что происходило в репозитории: захват аккаунта или CI часто виден именно там. Работает для пакетов со ссылкой на GitHub, приоритет — топ-пакеты.

- **Происхождение релиза:** есть ли attestation (PEP 740, Trusted Publishing), совпадают ли репозиторий и workflow с прошлыми релизами. Пакет годами публиковался через Trusted Publishing, а новая версия загружена API-токеном — сильный сигнал.
- **Релиз без следа в репозитории:** нет тега для версии, тег указывает на коммит вне основной ветки, тег перенесён на другой коммит.
- **Изменения CI перед релизом:** правки `.github/workflows`, особенно publish-workflow; новые `pull_request_target`, подстановка недоверенного ввода в `run:`, actions без пиннинга по SHA, кэш в релизном workflow.
- **Активность аккаунтов:** новый коллаборатор или автор коммитов прямо перед релизом, неподписанные коммиты у мейнтейнера, который обычно подписывает, активность в нетипичное время.
- **Внешние оценки:** OpenSSF Scorecard (Dangerous-Workflow, Token-Permissions, Pinned-Dependencies) и zizmor для статического анализа workflows.

Ограничения: лимит GitHub API — 5000 запросов в час с токеном, публичная лента событий хранит только последние 90 дней, а защита веток и deploy keys без прав администратора не видны.

## Скоринг и алерты

Риск релиза — число от 0 до 100: взвешенная сумма сигналов с поправкой на популярность пакета. На первом этапе веса задаются вручную в YAML, позже их можно подобрать логистической регрессией на размеченных данных.

| Уровень | Скор | Действие |
| --- | --- | --- |
| Critical | 80–100 | Мгновенный алерт в Telegram, постановка в очередь песочницы |
| High | 50–79 | Алерт в Telegram, отметка в дашборде |
| Medium | 20–49 | Только дашборд, дневной дайджест |
| Low | 0–19 | Сохраняется, не показывается |

- Комбинированные правила дают бонус: например, «новый пакет + тайпсквоттинг + сетевой вызов в `setup.py`» весит больше суммы частей.
- Allowlist пакетов и правил для подавления известных ложных срабатываний.
- Алерт содержит: пакет и версию, скор, топ-3 сигнала с фрагментами кода, ссылку на дифф в дашборде.
- Ручная разметка из дашборда (`malicious` / `benign`) сохраняется и идёт в оценку качества.

## Хранилище и модель данных

PostgreSQL для метаданных и результатов, S3-совместимое хранилище (MinIO локально) для артефактов. Артефакты храним 30 дней, подозрительные — бессрочно как доказательства.

| Таблица | Ключевые поля |
| --- | --- |
| `packages` | name, normalized\_name, first\_seen, downloads\_rank, is\_popular |
| `releases` | package\_id, version, published\_at, serial, maintainers, prev\_release\_id, status |
| `artifacts` | release\_id, filename, type (sdist/wheel), sha256, size, storage\_key |
| `analysis_runs` | release\_id, analyzer, analyzer\_version, started\_at, duration\_ms, error |
| `signals` | run\_id, rule\_id, severity, confidence, file\_path, line, evidence |
| `verdicts` | release\_id, score, level, decided\_by (auto/human), label, comment |

- `status` у релиза: `queued → downloaded → analyzed → alerted / clean / failed`.
- `analyzer_version` нужен, чтобы перепрогонять старые релизы при обновлении правил и сравнивать результаты.

## Оценка качества

Качество меряем на фиксированном бенчмарке: вредоносные пакеты из датасета DataDog против выборки обычных пакетов, плюс отдельный бенчмарк на диффы.

- **Позитивы:** пакеты из датасета DataDog (разделить по годам: обучение и подбор весов на старых, проверка на свежих).
- **Негативы:** 2000 случайных релизов с PyPI за месяц + 500 популярных пакетов (на них чаще всего ложные срабатывания).
- **Бенчмарк диффов:** синтетические атаки — берём настоящие пары версий популярных пакетов и внедряем в новую версию типовые вредоносные паттерны; плюс известные реальные случаи компрометации, если артефакты доступны.
- **Метрики:** recall и precision по уровням High+, false positive rate на 1000 релизов, задержка до вердикта.
- **Базовая линия:** стоковый GuardDog на том же наборе — проект должен быть не хуже по recall и лучше по FPR.
- Бенчмарк запускается в CI на каждое изменение правил, результаты пишутся в отчёт.

## Риски и открытые вопросы

Главный риск — поток ложных срабатываний, из-за которого алерты перестанут читать; главный вопрос безопасности — работа с живой малварью.

| Риск | Последствие | Что делаем |
| --- | --- | --- |
| Много ложных срабатываний | Алерты игнорируются | Лимит 20 алертов в день, allowlist, подбор весов на бенчмарке |
| Работа с вредоносными артефактами | Заражение хоста разработчика | Никогда не устанавливать пакеты вне песочницы, распаковка без выполнения кода, отдельная VM для песочницы |
| Побег из контейнера при динамике | Компрометация сервера | gVisor/Firecracker, отдельная VM без секретов в окружении; дома — изолированный VLAN без доступа к домашней сети |
| Нагрузка: тысячи релизов в день | Очередь растёт, задержка выше 10 минут | Приоритизация, лимит размера артефакта, горизонтальные воркеры |
