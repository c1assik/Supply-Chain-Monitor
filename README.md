# PyPI Supply Chain Monitor

Сервис следит за новыми релизами на PyPI и поднимает алерт, когда релиз похож на supply chain атаку.
Готовы этапы 1 и 2: поток релизов, статический анализ, дифф версий, скоринг и алерты. Из этапа 2б есть
проверка происхождения (PEP 740). Этап 4:
бенчмарк качества, подобранные по нему веса, дашборд и шаблон репорта. Цели и план описаны в спецификации.

## Запуск

```sh
deploy/generate-env.sh   # создаёт .env со случайными секретами
docker compose up --detach --build --wait
```

Для алертов нужно заполнить в `.env` значения `SCM_TELEGRAM_TOKEN` и `SCM_TELEGRAM_CHAT_ID`. Без секретов
из `.env` ни compose, ни приложение не запустятся: значений по умолчанию у них нет.

При смене паролей помните, что Postgres и Grafana применяют их только при создании своих томов: в
существующих томах пароль меняется через `ALTER ROLE` и `grafana cli admin reset-admin-password`.

Compose применяет миграции и запускает поллер и два воркера: основной и приоритетный для популярных
пакетов. При первом старте воркер загружает топ-5000
пакетов, дальше обновляет его каждую ночь. Без настроек Telegram алерты пишутся в лог воркера.

| Сервис | Адрес |
| --- | --- |
| Grafana (`admin` / `GRAFANA_PASSWORD`) | `http://localhost:3000` |
| Prometheus | `http://localhost:9090` |
| Дашборд | `http://localhost:8000` |

Правила в `deploy/prometheus/alerts.yml` срабатывают на падение потока до нуля и на p95 задержки выше
10 минут. В Prometheus их видно на странице Alerts, Alertmanager пока не подключён.

## Как устроен пайплайн

Поллер кладёт новые релизы в `releases` и очередь arq. Воркер ведёт релиз по стадиям, каждая из
которых коммитит результат вместе со следующим статусом:

| Стадия | Что делает | Статус после неё |
| --- | --- | --- |
| `download` | Метаданные PyPI, sdist и все wheel, предыдущая версия, проверка sha256, запись в S3 | `downloaded` |
| `analyze` | Безопасная распаковка обеих версий, анализаторы, запись `signals` | `analyzed` |
| `score` | Вердикт по `config/scoring.yaml` | `clean` или ждёт `alert` |
| `alert` | Сообщение в Telegram для High и Critical | `alerted` |

- Упавшая стадия повторяется `SCM_MAX_TRIES` раз, затем релиз получает `failed`.
- Раз в 5 минут `sweep` возвращает в очередь релизы, застрявшие после падения.
- Код из пакетов никогда не исполняется. Анализаторы и распаковка работают в пуле процессов, и воркер
  запускается без capabilities.

Что известно о релизе, показывает `pypi-monitor report <пакет> <версия>`: статус, с чем сравнивался,
вердикт и все сигналы.

### Файлы, загруженные после вердикта

Changelog сообщает о каждом загруженном файле (`add cp313 file ...`). Если файла не было в снимке PyPI,
с которым релиз прошёл стадии, релиз получает новую ревизию и проходит их снова: так ловится вредоносный
wheel под одну платформу, выложенный после чистых, или файл, догруженный в старую версию. Версия, которую
мы не видели, анализируется как новый релиз. Скачиваются только новые файлы, прогоны анализаторов и
автоматические вердикты прошлых ревизий остаются в истории, скорится только текущая. Повторный алерт
уходит, только если уровень вырос. Стадия, которая работала со старой ревизией, свои результаты не
записывает.

Популярные пакеты идут через отдельную очередь `arq:queue:priority` и воркер `worker-priority`, так что
всплеск обычных релизов не задерживает их вердикт. Очередь сохраняется на всех стадиях и при `sweep`.

### Источники релизов

RSS опрашивается раз в 45 секунд ради задержки, `changelog_since_serial` раз в 5 минут и при старте
ради полноты. Замеры от 31.10.2026: `updates.xml` отдаёт 100 записей, это около 20 минут потока;
`packages.xml` — около 40 записей; в будни выходит около 500 релизов в час. XML-RPC ограничен по
частоте, поэтому `user_packages` вызывается не чаще раза в 6 секунд, а сверх этого сигнал
`metadata.first_account_release` пропускается.

### Скоринг

Каждое правило считается один раз. Находки `threat-*` из GuardDog в коде, который исполняется сам,
получают правило `guarddog.install.*` и полный вес. В остальных файлах уверенность умножается на 0,2:
там эти правила в основном описывают обычные CLI-инструменты и агентов.

Что исполняется само, GuardDog и дифф решают одной функцией `role_of`:

- `setup.py` в корне sdist, `.pth`, `sitecustomize.py` и `usercustomize.py`, верхнеуровневый
  `__init__.py`, в том числе под `src/` и под `<name>.data/purelib|platlib/` в wheel: pip кладёт их
  в site-packages так же, как корень wheel.
- Модули, до которых от этих файлов доходят импорты уровня модуля, включая относительные,
  `__import__("x")` и `importlib.import_module("._core", __name__)` с `package=` в любом виде
  (`analyzers/startup.py`). В таком модуле находка считается install-кодом, только если её строка
  исполняется при импорте: верхний уровень и функции, которые он вызывает или передаёт в
  `Thread`/`atexit`, а также методы, до которых он доходит через класс: `C().run()`, `C.go()`, property,
  `obj = C(); obj.run()`, `with C():`, `self.helper()` внутри выполняемого метода, методы базовых классов
  того же модуля (`analyzers/execution.py`). Тело `if __name__ == "__main__"` не считается.
- Тесты, вендоринг и сгенерированный код не повышаются, даже если их кто-то импортирует.

Ложные срабатывания подавляются через `allowlist` в `config/scoring.yaml`.

### Дифф версий

Новый релиз сравнивается с предыдущей версией по PEP 440: sdist с sdist, wheel с wheel. Базой становится
старшая из младших версий, которую мог установить пользователь: yanked не считается, а финальный релиз
сравнивается с финальным. Иначе нагрузка, выложенная сначала в yanked-версии или pre-release, не попала
бы в дифф релиза, который её распространяет. Версия, которую мы не обрабатывали, сохраняется со статусом
`baseline`: её артефакты лежат в S3, но она не анализируется и не получает вердикт.

| Анализатор | Что ищет |
| --- | --- |
| `diff` | Новые файлы, `.pth`, entry points, build backend; по AST новые импорты, опасные вызовы, URL и IP; бинарники, скрипты и непрозрачные блобы |
| `consistency` | Код wheel, которого нет в sdist; код релиза, расходящийся с тегом на GitHub |
| `context` | Смена владельцев, релиз после года затишья, скачок мажорной версии |
| `provenance` | Пропажа PEP 740 attestations у проекта с Trusted Publishing, смена репозитория или workflow публикации |

- Форматирование, комментарии, докстринги и номер версии изменением не считаются.
- Если общего вида артефактов нет, например wheel выложен в проект, где раньше были только sdist,
  сравнивается то, что есть: смена формата не должна отключать дифф.
- Файлы делятся на роли. Код, исполняемый сам (`setup.py`, `.pth`, верхнеуровневый `__init__.py`), даёт
  правила `diff.install.*`. Вендоринг, сгенерированный код, тесты и файлы sdist, не попавшие в wheel,
  дают правила `noise.*` с низкой уверенностью и не участвуют в комбинациях.
- Факт «исполняется при импорте» учитывает функции, вызванные на верхнем уровне: `def _go(): ...` и
  `_go()` в обычном модуле дают `diff.install.new_dangerous_call`.
- Файлы, которые не читаются как код, определяются по сигнатуре, а не по расширению. Сигнатуре
  медиа и данных верят, только если сходится структура: CRC чанков PNG, цепочка маркеров JPEG,
  таблицы TrueType, размеры RIFF/WOFF/ICO и так далее (`analyzers/content.py`). Четыре байта
  заголовка PNG перед случайными байтами — это блоб. Веса без сигнатуры (`model.bin`) проверяются
  по раскладке safetensors/pickle/GGUF и по тому, что это массив чисел, а не случайные байты.
- Архивы внутри артефакта (zip, jar, gz, bz2, xz, tar, вложенные до трёх уровней) читаются в
  памяти с лимитами: до 1000 членов и 64 МБ распакованных байт на файл, у каждого члена только
  начало, если это не архив. Архив получает вид самого опасного члена: `exe` в zip — бинарник.
- Новый или изменённый бинарник в sdist или чистом wheel даёт `diff.file.new_binary` / `binary_changed`. В
  platform wheel бинарники пересобираются в каждом релизе, поэтому изменения сводятся в один сигнал-улику
  `platform_binaries_changed`, который весит только в комбинации со сменой владельцев, затишьем или
  пропажей attestations. Новый скрипт (`.sh`, `.ps1`, `.js`, shebang) — улика `new_script`, а скрипт,
  который скачивает или декодирует (`curl`, `iex`, `FromBase64String`, ...), — `new_script_fetches`.
  Блоб без известного формата с энтропией от 7,5 бит на байт или с длинной строкой base64 —
  `new_blob`; в связке с новым опасным вызовом это дроппер. Изменённый скрипт сравнивается с прошлым
  построчно: строка с `curl`, `iex` и прочим из `SCRIPT_FETCHES`, которой раньше не было, даёт тот же
  `new_script_fetches` (`curl ... | sh` в существующем `install.sh`).
- Все wheel релиза читаются. Первый (чистый, иначе самый маленький) сравнивается с прошлой версией как
  раньше. У остальных остаются только файлы, которых нет ни в первом, ни в предыдущих
  (`pipeline/wheels.py`): общий Python-код платформенных wheel читается один раз. Эти файлы сканирует
  GuardDog (граф импортов строится поверх первого wheel), сравнивает с sdist `consistency`, а дифф
  сравнивает с wheel той же платформы прошлой версии, затем с первым wheel. Больше 64 wheel не читается.
- Обычные модули сравниваются со всем прошлым релизом, чтобы перенос кода не выглядел новым. Цена:
  вызов, который уже был в другом модуле пакета, сигнала не даст. Файлы с автозапуском сравниваются
  только сами с собой, а `exec` декодированных данных сигналит всегда.
- Владельцы сравниваются только с нашими снимками: PyPI для старых версий показывает сегодняшних.
  Поэтому смена владельцев видна со второго обработанного релиза пакета.
- Provenance запрашивается, только если у предыдущей версии были attestations: simple API отдаёт это
  без лишних запросов, а издатель берётся из `/integrity/.../provenance`. Проверяется каждый файл
  релиза, в том числе слишком большие для анализа: wheel без attestations рядом с подписанными — это
  загрузка в обход CI. Сравниваются файлы того же типа: если раньше attestations были только у sdist,
  wheel без них сигнала не даст.
- Сверка с тегом идёт только для популярных пакетов и через codeload, вне лимита GitHub API. Тег ищется
  по шаблонам `v1.0`, `1.0`, `name-1.0`, `name-v1.0`, `release-1.0`, `name@1.0`. Отсутствие тега не
  сигнал, это задача этапа 2б. Отключается через `SCM_COMPARE_TAGS=false`.

Бенчмарк: `.venv/bin/python -m benchmarks.diff_pairs`. Это сотни синтетических пар «чистая/заражённая
версия», которые строятся в памяти. Он работает как тест, поэтому правила нельзя изменить так, чтобы
потерять recall или получить ложный алерт незаметно.

## Дашборд

Лента вердиктов High и Critical, по умолчанию только неразмеченные. Medium включается фильтром, Low не
показывается. Из карточки релиза видны сигналы и упавшие анализаторы, дифф с предыдущей версией и разметка
`malicious` / `benign`. Метка записывается отдельным вердиктом `human` рядом с автоматическим, история
сохраняется, действует последняя. Алерты в Telegram ведут на дифф, адрес задаёт `SCM_DASHBOARD_URL`.

Страница «Репорт в PyPI» собирает готовый текст с хэшами и уликами. Он отправляется вручную через
Report project as malware на странице проекта. Сервис сам ничего никуда не отправляет.

Содержимое страниц пишут атакующие: всё экранируется, CSP запрещает встроенный код, а разметка принимается
только с заголовком htmx, который чужой сайт поставить не может. Авторизации нет, порт открыт только на
`127.0.0.1`. На VPS дашборд нужно открывать через SSH-туннель, а другие имена хоста добавлять в
`SCM_DASHBOARD_ALLOWED_HOSTS`.

## Качество

Бенчмарк на реальных данных сравнивает 2532 образца малвари из датасета DataDog (коммит закреплён) с
20497 обычными релизами: 20000 случайных (2000 за октябрь 2026 и 18000 за 30 дней до 03.11.2026) и
топ-500 по загрузкам. Список негативов заморожен в `benchmarks/data/negatives.json`. Подбор весов идёт на
train, проверка на test: малварь делится по году обнаружения (test — с 2025), негативы по хэшу имени.

```sh
.venv/bin/python -m benchmarks.malware scan --stream   # 4–5 часов на 7 процессах
.venv/bin/python -m benchmarks.malware report          # секунды: скоры считаются из сохранённых сигналов
```

Все негативы занимают около 30 ГБ, поэтому `--stream` скачивает их пачками по 400 и удаляет каждую пачку
после скана; на диске одновременно не больше двух пачек. Без флага скачанное остаётся, как нужно кэшу в
CI. Релиз, которого больше нет на PyPI, учитывается как «удалён» и в метрики не входит.

В `.benchmark/` лежит живая малварь. Она распаковывается с лимитами продакшена и читается как данные;
не запускайте из этого каталога ничего и не открывайте его в IDE с автоисполнением.

Результаты от 03.11.2026 на test, цели спецификации выполнены:

| Метрика | Монитор | GuardDog при том же бюджете | Стоковый GuardDog | Цель |
| --- | --- | --- | --- | --- |
| Recall High+ | 47,1% | 0,2% | 87,1% | не ниже GuardDog при том же бюджете |
| Recall Medium+ | 79,9% | | | |
| FPR | 0,15% | | 81,2% | ниже GuardDog |
| Алертов в день | 18 | 18 | 9791 | до 20 |

На train те же веса дают recall 72,3% (Medium+ 95,1%) и 14 алертов в день. Оценка потока: 11750
обычных и 300 популярных релизов в сутки, замер по changelog за октябрь 2026. На test теперь около 6000
случайных релизов, и один ложный алерт стоит около 2 алертов в день вместо 22 на прежних 2000.

Это изменило картину. Прежние веса, проверенные на 20000 негативов, дают на test не 2, а 20 алертов в
день, на train 25: «2 в день» были шумом выборки. Подбор на новом корпусе ставит порог по бюджету с
запасом 1,06 вместо 1,2 и целится в 15 алертов в день out-of-fold, чтобы предел 20 держался и на
релизах, которых модель не видела. Recall на test вырос с 46,4% до 47,1%, Medium+ с 70,0% до 79,9%.
Правила вроде `install.threat-network-reverse-shell` и `install.threat-runtime-system-info` больше не
алертят в одиночку: на 18000 новых негативах они сработали на обычных релизах.

Стоковый GuardDog срабатывает на любую находку, это 81% обычных релизов и около 10 тысяч алертов в день.
Поэтому с recall сервиса сравнивается GuardDog при том же бюджете (`guarddog_recall_at_budget`): релизы
ранжируются по числу сработавших правил, всех или только `threat-*`, и порог ставится так, чтобы поток
был не больше нашего. Число находок GuardDog малварь почти не отделяет: чтобы уложиться в 18 алертов в
день, нужно 12+ правил `threat-*`, и recall падает до 0,2%. Без правил `capability-*` у стокового
GuardDog 77,4% recall и 37,5% FPR.

Свежая малварь часто вообще не исполняется сама (`threat-network-exfil-sysinfo` в обычной функции —
частый пропуск), и это уже вопрос собственных правил.

Веса `guarddog.*` и `metadata.*` подбирает `python -m benchmarks.tune` (около 30 минут): неотрицательная
логистическая регрессия на train. Сила L2-регуляризации и запас над порогом High выбираются
кросс-валидацией на train с разбиением по пакетам: запас — минимальный, при котором out-of-fold поток
укладывается в 15 алертов в день. Результат переносится в `config/scoring.yaml`, цифры на test для
подбора не используются. Отрицательных весов нет, иначе безобидный код снижал бы риск. Алертить в
одиночку может только `guarddog.install.threat-*`, сработавшее на малвари 5+ раз и ни разу на обычных
релизах; `capability-*` описывают обычный код, и корпус такого размера не доказывает обратного.
Метаданные ограничены так, что без находок в коде алерта не дают. Веса диффа, контекста и provenance
остаются ручными.

### Дифф на реальных релизах

`benchmarks.real_diff` сравнивает настоящие атаки и обновления с предыдущей версией с PyPI, выбранной
так же, как в продакшене, и добавляет сигналы диффа к уже сохранённым сканам.

```sh
.venv/bin/python -m benchmarks.real_diff scan     # после malware scan: ещё около 12 ГБ и 15 минут
.venv/bin/python -m benchmarks.real_diff report
```

Обновления берутся из стабильной части списка негативов, 2000 случайных и все популярные, и
докачиваются, если их нет на диске. Результаты пишутся в `real_diff.v<версия диффа>.jsonl`, так что
скан прошлой версии анализатора за новый не сойдёт.

Результаты от 02.11.2026, до доработок второго ревью (форматы, архивы, скрипты, все wheel). Перемерить их
03.11 не удалось: на диске не хватило места на прошлые версии.

| Выборка | Только статика | Статика и дифф |
| --- | --- | --- |
| Захваченные библиотеки, все | 7 / 29 | 21 / 29 |
| Первый заражённый релиз | 3 / 17 | 13 / 17 |
| Продолжение атаки | 4 / 11 | 8 / 11 |
| Случайные обновления, ложные алерты | 0 / 1792 | 4 / 1792 |
| Популярные обновления, ложные алерты | 5 / 496 | 8 / 496 |

На всех негативах дифф поднимает поток с 3 до 28 алертов в день. До доработок по ревью было 19 / 29 при
54 алертах: прибавку дал учёт функций, вызываемых при импорте, а ложные алерты снизились вместе с весами
статики. Новые сигналы по бинарникам, скриптам и блобам на этом корпусе атак не добавили (нагрузка там
в Python) и весят только в комбинациях с признаками захвата: вместе с новым опасным вызовом они давали
ложные алерты на обычных релизах вроде `pandas` 3.1.0.

- «Продолжение атаки» — релиз, у которого между базой и им есть удалённая заражённая версия. В день атаки
  базой могла быть она, и тогда дифф был бы пуст. Для этих релизов результат оптимистичный.
- Пропуски: нагрузка в обычном модуле, где те же импорты и вызовы уже были в пакете (`litellm`, `telnyx`,
  `ultralytics` 8.3.41). Это известная цена сравнения модулей со всем прошлым релизом.
- `nhmpy` удалён с PyPI целиком, сравнивать не с чем.
- Веса диффа на этих 29 образцах не подбирались: их слишком мало, и проверять было бы не на чем.

### Что бенчмарк не измеряет

- Дифф в основном прогоне: в датасете нет предыдущих версий. Его меряют `benchmarks.real_diff` выше и
  синтетический `benchmarks.diff_pairs`.
- Сигналы возраста, владельцев и списка файлов: они есть только у негативов и выдали бы метку. Метаданные
  обоих классов берутся из `PKG-INFO`, поэтому `metadata.new_package` и комбинации с ним здесь не работают,
  и recall в продакшене должен быть выше.
- Provenance: в датасете нет истории публикаций. Сигналы проверены тестами пайплайна с фейковым PyPI.
- Задержку до вердикта: она видна в метрике Prometheus.
- GuardDog запускается только с правилами кода, его правила метаданных ходят в сеть.

В CI джоб `benchmark` считает те же метрики на всех позитивах и 300 негативах каждой группы и падает при
ухудшении относительно `benchmarks/data/quality_floor.json`. Это защита от регрессий, а не цель: если
качество стало лучше, порог поднимается через `report --negatives 300 --update-floor`.

Список негативов пересобирается через `python -m benchmarks.negatives`, но метрики разных списков не
сравниваются.

## Разработка

Нужны Python 3.12+ и Docker с Compose. Под Python 3.14 у `pygit2` и `yara-python` нет готовых wheels:
понадобятся компилятор и `libgit2`. Образ и CI используют 3.13.

```sh
python -m venv .venv
.venv/bin/pip install -e . --group dev
.venv/bin/pre-commit install
deploy/generate-env.sh
```

Окружение и схема БД:

```sh
docker compose up --detach --wait
.venv/bin/alembic upgrade head
```

| Сервис | Адрес |
| --- | --- |
| PostgreSQL | `localhost:5432` |
| Redis | `localhost:6379` |
| S3 (SeaweedFS) | `http://localhost:8333` |

Проверки:

```sh
.venv/bin/ruff check .
.venv/bin/ruff format --check .
.venv/bin/mypy
TEST_DATABASE_URL=postgresql+psycopg://scm:<POSTGRES_PASSWORD>@localhost:5432/scm_test .venv/bin/pytest
```

Без `TEST_DATABASE_URL` тесты миграций пропускаются. База из этой переменной очищается при каждом
запуске, поэтому она должна быть отдельной:

```sh
docker compose exec postgres createdb -U scm scm_test
```

Новая миграция после изменения `src/pypi_monitor/db/models.py`:

```sh
.venv/bin/alembic revision --autogenerate -m "описание"
```
